\chapter{Diseño e implementación}
\label{chap:diseno}
En este capítulo se describe el diseño e implementación del código para el cálculo de la dispersión estelar basada en el algoritmo de Barnes–Hut.
Se presentan la arquitectura del sistema, las estructuras de datos empleadas y los algoritmos principales, así como las decisiones de implementación que permiten su ejecución eficiente en arquitecturas paralelas.
En particular, se desarrollan y analizan dos versiones paralelas: una versión CPU basada en paralelización mediante OpenMP que tiene como objetivo los sistemas  multicore y una versión GPU que aprovecha la capacidad de cómputo masivo de aceleradores NVIDIA mediante CUDA\@.

\section{Obtención y preparación de los datos}\label{sec:datos}

Para realizar la simulación fue necesario disponer de varios subconjuntos de datos procedentes del catálogo \textit{Gaia DR3} y del catálogo complementario de distancias \texttt{GeDR3Dist}.
El proceso completo comprendió la descarga, reducción y combinación de los distintos catálogos, con el objetivo de obtener un conjunto coherente de parámetros espaciales, fotométricos y físicos.

\subsection*{Descarga de los catálogos principales}

Los catálogos \texttt{gaia\_source} y \texttt{astrophysical\_parameters} se descargaron desde el \textit{Gaia Archive}~\cite{gaia_archive} mediante el comando \texttt{wget}, automatizando la obtención de archivos comprimidos en formato \texttt{.csv.gz}:

\begin{verbatim}
wget -r -np -nd -A "*.csv.gz" "URL_archivos"
\end{verbatim}

Cada archivo contiene un subconjunto del catálogo dividido por rangos de \texttt{source\_id}, lo que facilita la descarga y el procesamiento distribuido.
El tamaño total de la descarga es de aproximadamente 757~GB para la tabla \texttt{gaia\_source} y 258~GB para \texttt{astrophysical\_}\allowbreak\texttt{parameters}, sumando un total de 3.386 archivos en cada caso.
\subsection*{Descarga del catálogo de distancias}

Las estimaciones de distancia derivadas del paralaje se obtuvieron a partir del catálogo \texttt{I/352/GeDR3Dist}, disponible a través del servicio \textit{TAPVizieR}.
Dado el volumen de datos (más de mil millones de fuentes), se diseñó un script en \texttt{bash} que divide el rango de \texttt{source\_id} en bloques y realiza consultas ADQL (\textit{Astronomical Data Query Language}) sucesivas al servidor.
Este script se puede consultar en Listing~\ref{lst:script_descargar_distances} del Anexo A.

De esta forma se obtuvieron diversos archivos \texttt{.csv} con los campos \texttt{Source} y \texttt{rgeo}, que posteriormente se integraron en el conjunto de datos principal.
\subsection*{Reducción de columnas}

Con el fin de optimizar el almacenamiento y acelerar las operaciones de lectura, los archivos originales se redujeron manteniendo únicamente las columnas relevantes para el análisis:
\texttt{source\_id}, \texttt{ra}, \texttt{dec}, \texttt{pmra}, \texttt{pmdec}, \texttt{radial\_velocity} y \texttt{bp\_rp}.
El filtrado se realizó mediante un script en AWK y utilizando \texttt{parallel} para acelerar el proceso, generando versiones compactas de los catálogos.
El script se puede consultar en el Listing~\ref{lst:script_reducir_astro} del Anexo A.
\subsection*{Combinación de catálogos}

Finalmente, los catálogos reducidos se combinaron utilizando un script en \texttt{Python} con las librerías \texttt{pandas} y \texttt{duckdb} (Ver Listing~\ref{lst:script_combinar} del Anexo A).
Primero se creó una base de datos temporal con las distancias debido al diferente número de archivos por tabla y el orden de IDs, y posteriormente se fusionaron los catálogos mediante uniones internas sobre el campo \texttt{source\_id}, aprovechando el procesamiento en paralelo para reducir el tiempo de ejecución:

\begin{verbatim}
merged = pd.merge(main_df, astro_df, on='source_id')
merged = pd.merge(merged, distance_df, on='source_id')
\end{verbatim}

El resultado final fue un conjunto de 3.386 archivos optimizados \texttt{merged\_XXXX.csv}, listos para el filtrado y el análisis posterior ocupando 223~GB sin comprimir.

Este procedimiento permitió manejar de forma eficiente el volumen total del catálogo (más de 1.800 millones de fuentes en \textit{Gaia DR3}), garantizando coherencia y consistencia entre todos los parámetros empleados.

\section{Estructuras de datos principales}\label{sec:estructuras}
El sistema utiliza varias estructuras de datos fundamentales que son compartidas entre la versión CPU y GPU, además de otras especializadas en cada versión.
Estas estructuras están diseñadas para optimizar tanto el acceso a memoria como la compatibilidad con los modelos de paralelización disponibles.

\subsection{Estructura de estrella (\texttt{Star})}\label{subsec:estructura-de-estrella-(texttt{star})}

La estructura central del sistema es \texttt{Star}, que agrupa los parámetros astrométricos, cinemáticos y físicos de cada objeto celeste.
Esta estructura se organiza de forma \textit{structure-of-arrays} (SoA) en lugar de arrays de estructuras, permitiendo optimizar el acceso a memoria en operaciones paralelas y facilitar la vectorización automática en CPU y GPU.

La selección de tipos de datos en cada campo responde a criterios de precisión numérica y eficiencia de memoria:

\begin{itemize}
    \item \textbf{Precisión doble (\texttt{double}, 64 bits)}:
    \begin{itemize}
        \item \texttt{ra}, \texttt{dec}, \texttt{distance}, \texttt{pmra}, \texttt{pmdec}, \texttt{radial\_velocity}: Los datos originales de Gaia DR3 se proporcionan en precisión doble. Mantenerlos así preserva la precisión astrométrica y es necesario para transformaciones de coordenadas que acumulan errores.

        \item \texttt{Cx}, \texttt{Cy}, \texttt{Cz}, \texttt{Vx}, \texttt{Vy}, \texttt{Vz}: Las coordenadas cartesianas heliocéntricas y velocidades se mantienen en doble precisión para garantizar estabilidad numérica durante la integración temporal de órbitas a lo largo de millones de años. Los errores de redondeo en precisión simple acumularían desviaciones significativas en las trayectorias.
    \end{itemize}

    \item \textbf{Precisión simple (\texttt{float}, 32 bits)}:
    \begin{itemize}
        \item \texttt{mass}, \texttt{color}: Estos parámetros representan propiedades físicas derivadas o fotométricas con precisión inherente limitada.
        Usar precisión simple reduce el consumo de memoria a la mitad en estos campos sin pérdida práctica de información.
    \end{itemize}

    \item \textbf{Identificador de 64 bits sin signo (\texttt{unsigned long})}:
    \begin{itemize}
        \item \texttt{id}: Identificador único de Gaia DR3, necesario para relacionar datos con el catálogo original.
    \end{itemize}
\end{itemize}

Por tanto, la memoria por estrella será:
\begin{itemize}
    \item \texttt{id}: 8 bytes $\times$ 1 = 8 bytes
    \item \texttt{ra}, \texttt{dec}, \texttt{distance}, \texttt{pmra}, \texttt{pmdec}, \texttt{radial\_velocity}: 8 bytes $\times$ 6 = 48 bytes
    \item \texttt{Cx}, \texttt{Cy}, \texttt{Cz}, \texttt{Vx}, \texttt{Vy}, \texttt{Vz}: 8 bytes $\times$ 6 = 48 bytes
    \item \texttt{color}, \texttt{mass}: 4 bytes $\times$ 2 = 8 bytes
    \item \textbf{Total por estrella: 140 bytes}
\end{itemize}

Tal y como se comentó en la Sección~\ref{sec:filtrado}, en este proyecto simularemos aproximadamente 1.100 millones de estrellas, por lo que la memoria requerida sería:

\[
    1.1 \times 10^9 \times 140 \text{ bytes} = 143.42 \text{ GB}
\]
tamaño perfectamente abarcable en los nodos disponibles en el Finisterrae III de 256 GB de RAM (ver Sección~\ref{subsec:especificaciones-tecnicas-de-los-nodos}).

Tras la carga completa de un bloque de estrellas y la realización de los cálculos preliminares (transformación de coordenadas y estimación de masas), ciertos campos astrométricos originales dejan de ser necesarios y son liberados para reducir el consumo de memoria:

\begin{itemize}
    \item \texttt{ra}, \texttt{dec}, \texttt{distance}: Tras convertir a coordenadas cartesianas heliocéntricas (\texttt{Cx}, \texttt{Cy}, \texttt{Cz}), estos datos ecuatoriales ya no son necesarios.

    \item \texttt{pmra}, \texttt{pmdec}, \texttt{radial\_velocity}: Tras convertir a velocidades cartesianas (\texttt{Vx}, \texttt{Vy}, \texttt{Vz}), estos datos originales no vuelven a usarse.

    \item \texttt{color}: Tras estimar \texttt{mass} mediante la relación masa-luminosidad que utiliza estos parámetros, pueden ser liberados si no se requieren en resultados finales.
\end{itemize}
Liberando los siete campos astrométricos originales se reduce el consumo en 52 bytes por objeto, correspondiendo a una reducción del 37.1\% respecto al consumo total por estrella.
Para 1.100 millones de estrellas, esto libera aproximadamente 53.27 GB de memoria.

Este diseño permite un balance entre precisión numérica, eficiencia de memoria y adaptabilidad a diferentes infraestructuras y volúmenes de datos, siendo crucial para gestionar simulaciones de escala galáctica en entornos de computación de altas prestaciones.

\subsection{Estructura de arbol CPU (\texttt{Octree})}\label{subsec:estructura-de-arbol-cpu(texttt{octree})}
La construcción del árbol octal (Octree) es un paso fundamental en el método de Barnes–Hut, ya que permite organizar las estrellas espacialmente de forma jerárquica para aproximar interacciones gravitatorias lejanas.
Cada nodo del árbol representa un cubo en el espacio, caracterizado por una masa total contenida, el centro de la masa acumulada y el tamaño del nodo.
El nodo puede contener una o varias estrellas (nodo hoja), u ocho nodos hijos (subdivisión del espacio), cada uno correspondiente a uno de los octantes.

La estructura \texttt{Octree} implementa el árbol jerárquico utilizado en la versión CPU.
A diferencia de la estructura \texttt{Star}, que es plana y homogénea, el octree es una estructura jerárquica donde cada nodo contiene referencias a hasta ocho nodos hijos.

Cada nodo del octree almacena información geométrica, propiedades físicas acumuladas e información topológica:

\begin{itemize}
    \item \textbf{Geometría del volumen (precisión simple, \texttt{float})}:
    \begin{itemize}
        \item \texttt{center\_x}, \texttt{center\_y}, \texttt{center\_z}: Coordenadas del centro del cubo.

        \item \texttt{half\_size}: Semiextensión del cubo en cada dirección.

        La geometría del árbol se utiliza únicamente para aplicar el criterio de apertura de Barnes-Hut (comparación de distancias).
        La precisión simple es suficiente para estas comparaciones relativas sin afectar la validez del criterio de agrupación.
    \end{itemize}

    \item \textbf{Propiedades físicas (masa en \texttt{float}, centro de masas en \texttt{double})}:
    \begin{itemize}
        \item \texttt{mass}: Masa total acumulada del nodo y sus descendientes.
        La masa total se almacena en precisión simple ya que es el resultado de sumas acumulativas que se recomputabilizan en cada construcción del árbol.

        \item \texttt{com\_x}, \texttt{com\_y}, \texttt{com\_z}: Centro de masas.
        Se mantiene en precisión doble porque:
        \begin{enumerate}
            \item Se utiliza directamente en el cálculo de la aceleración gravitatoria.
            \item Se actualiza mediante una operación de media ponderada que puede acumular errores significativos en precisión simple.
            \item La precisión en la localización del centro de masas afecta directamente a la exactitud de la aproximación multipolar.
        \end{enumerate}
    \end{itemize}

    \item \textbf{Información topológica}:
    \begin{itemize}
        \item \texttt{children}: Array de ocho referencias a nodos hijos (array de ocho enteros sin signo).
        Se utiliza \texttt{unsigned int} en lugar de \texttt{long} por dos razones críticas:
        \begin{enumerate}
            \item \textbf{Ahorro de memoria}: Cada referencia ocupa 4 bytes, reduciendo en un 50\% el espacio dedicado a punteros.

            \item \textbf{Límite máximo de nodos}: El rango de \texttt{unsigned int} es de 0 a $2^{32} - 1 = 4{.}294{.}967{.}295$, más que suficiente para los nodos esperados en una simulación de 1.100 millones de estrellas.
        \end{enumerate}

        Para representar la ausencia de hijo se utiliza la constante \texttt{INVALID\_INDEX} = \texttt{UINT32\_MAX} (4.294 mil millones), un valor fuera del rango de nodos válidos.
        Aunque \texttt{unsigned int} no permite directamente valores negativos como -1, el uso de \texttt{UINT32\_MAX} es una estrategia estándar que proporciona semántica equivalente: una comparación \texttt{if (child == INVALID\_INDEX)} determina de forma unívoca si el hijo existe.

        \item \texttt{star\_index}: Índice de la estrella si el nodo es una hoja, o -1 si es un nodo interno, se utiliza \texttt{long}.
        Este campo mantiene precisión de 64 bits porque son los mismos valores que los almacenados en Star.
    \end{itemize}
\end{itemize}

Por tanto, la memoria por nodo del octree será:
\begin{itemize}
    \item \texttt{center\_x}, \texttt{center\_y}, \texttt{center\_z}, \texttt{half\_size}: 4 bytes $\times$ 4 = 16 bytes
    \item \texttt{mass}: 4 bytes
    \item \texttt{com\_x}, \texttt{com\_y}, \texttt{com\_z}: 8 bytes $\times$ 3 = 24 bytes
    \item \texttt{children[8]}: 4 bytes $\times$ 8 = 32 bytes
    \item \texttt{star\_index}: 8 bytes
    \item \textbf{Total por nodo: 88 bytes}
\end{itemize}

\subsection{Estructura de arbol GPU (\texttt{OctreeGPU})}\label{subsec:estructura-de-arbol-gpu(texttt{octreegpu})}
La estructura \texttt{OctreeGPU} implementa el árbol jerárquico para la versión acelerada por GPU\@.
Aunque mantiene la misma lógica algorítmica que la versión CPU, su organización física es fundamentalmente diferente, porque se ha optimizado para:
\begin{enumerate}
    \item Maximizar el acceso coalescente a memoria en GPU (acceso contiguo a memoria)
    \item Minimizar las divergencias de control entre hilos CUDA
    \item Reducir la necesidad de sincronización global entre dispositivos
    \item Facilitar la paralelización masiva de búsquedas en el árbol
\end{enumerate}

En lugar de un único árbol monolítico como en CPU, la versión GPU divide el árbol raíz en ocho subárboles independientes, uno para cada octante del espacio:

\begin{lstlisting}[language=C,label={lst:octree_gpu_struct},caption={Estructura OctreeGPU con partición en octantes}]
typedef struct {
    OctreeOctant *octants[8];    // 8 subárboles independientes
    FrontierGPU *frontier[8];    // 8 fronteras multipolo
} OctreeGPU;
\end{lstlisting}

Esta partición ofrece ventajas significativas:

\begin{itemize}
    \item \textbf{Paralelización natural}: Los ocho octantes se construyen en paralelo durante la etapa de inicialización.
    Cada hilo construye un octante sin contención con los otros.

    \item \textbf{Eficiencia de memoria GPU}: Cada octante se transfiere a la GPU como un bloque de memoria contiguo, evitando la busqueda de hijos por rama como en CPU.

    \item \textbf{Escalabilidad multi-GPU}: En sistemas con múltiples aceleradores, cada octante puede asignarse a una GPU diferente, lo que permite distribuir la carga de trabajo de forma natural.

\end{itemize}

A diferencia de la versión CPU, donde cada nodo se almacena de forma distribuida en arrays separados (SoA), en GPU cada nodo individual se organiza como una estructura compacta \texttt{OctreeNode} (\textit{Array of Structures}, AoS) que contiene los mismos datos en una única unidad de memoria.
Esto se debe a que en GPU el costo de divergencia de control al acceder a múltiples arrays dispersos es mayor que el costo de leer una estructura compacta.
Como cada hilo de CUDA que desciende por el árbol accede a un único nodo a la vez, tener todos los datos del nodo juntos en memoria maximiza la localidad espacial, mejorando la tasa de accesos coalescentes a memoria.

Debido a la baja eficiencia en la implementación de funciones recursivas en GPU, la arquitectura CUDA requiere un enfoque iterativo para recorrer el árbol que evite el uso de stack implícito.
El campo \texttt{next} añadido a la estructura \texttt{OctreeNode} implementa un enlace al siguiente nodo relevante, convirtiendo la búsqueda recursiva del árbol en una iteración directa sobre una lista encadenada de nodos no-hoja.
\begin{lstlisting}[language=C,caption=Estructura OctreeNode,label={lst:lstlisting4}]
typedef struct {
    float center_x, center_y, center_z;
    float half_size;
    float mass;
    double com_x, com_y, com_z;
    unsigned int children[8];
    long star_index;
    unsigned int next;
} OctreeNode;
\end{lstlisting}

Debido a la subdivisión por octantes, es necesario representar una porción del resto de subárboles y la frontera multipolo cumple este propósito fundamental.
La frontera multipolo \texttt{FrontierGPU} es la estructura de datos central que representa la aproximación del campo gravitatorio generado por el resto del árbol.
En lugar de enumerar explícitamente todos los nodos que contribuyen a la aceleración de una partícula (lo cual generaría divergencia masiva entre hilos), se mantiene una lista compacta de nodos que conforman la frontera válida según el criterio de apertura de Barnes-Hut.

\section{Diseño algorítmico y paralelización}\label{sec:diseno-algoritmico-y-paralelizacion}

En esta sección se describen los algoritmos principales empleados en la simulación, las estrategias de paralelización aplicadas en las versiones CPU (OpenMP) y GPU (CUDA) y las decisiones de diseño que permiten un uso eficiente de memoria y cómputo.

El sistema paralelo se estructura en tres bloques principales: la gestión de la entrada y salida de datos, la construcción del árbol jerárquico de Barnes-Hut y la simulación dinámica de la dispersión estelar.

La fase de entrada y salida se implementa de forma paralela mediante OpenMP y es común a ambas versiones del código, CPU y GPU, permitiendo un procesado eficiente de un gran volumen de datos.

La construcción del árbol de Barnes-Hut presenta dos enfoques paralelos diferenciados según la arquitectura.
En la versión CPU se emplea OpenMP para paralelizar los cálculos asociados a la inserción de partículas y al cómputo de propiedades agregadas de los nodos.
En la versión GPU, en cambio, el árbol se organiza en octantes independientes para maximizar el paralelismo masivo, sustituyendo el recorrido recursivo utilizado en CPU por un enfoque iterativo sin pila (stackless), más adecuado para su ejecución en CUDA.

Finalmente, la simulación de la dispersión estelar, también se implementa en paralelo usando OpenMP en la versión CPU y CUDA en la versión GPU, haciendo especial énfasis en la optimización del acceso a memoria y la reducción de latencias.

\subsection{Entrada y salida}\label{subsec:lectura-de-archivos}

Dado el volumen de datos manejado (millones de estrellas), las operaciones de entrada y salida (\textit{E/O}) constituyen una parte crítica del rendimiento global del sistema.
Tanto la lectura inicial, como la escritura de resultados, se han diseñado para ser escalables y eficientes en entornos de cómputo paralelo.
La lectura se realiza mediante un modelo distribuido por archivos y procesado por bloques, optimizado para entornos de CPU multi-hilo:

\begin{enumerate}
    \item \textbf{Distribución de ficheros entre hilos:}
    Se escanea el directorio de entrada y se genera una lista de ficheros CSV válidos.
    Su procesamiento se paraleliza mediante \texttt{\#pragma omp parallel for} con \textit{schedule(dynamic)}, permitiendo adaptarse a diferencias en tamaño de archivo y equilibrando la carga de trabajo entre hilos.

    \item \textbf{Procesamiento por bloques de lectura:}
    Cada fichero se lee mediante \texttt{fread} en bloques de tamaño fijo (\texttt{BLOCK\_SIZE}), evitando cargar el archivo completo en memoria.
    Para manejar líneas cortadas entre dos bloques se mantiene un fragmento residual (\textit{leftover}) que se concatena con la lectura siguiente hasta completar la línea.
    Esta estrategia reduce el número de operaciones de E/S y mejora el rendimiento respecto a \texttt{fgets}.

    \item \textbf{Tokenización y validación:}
    Cada línea se tokeniza utilizando \texttt{strtok\_r}\footnote{La función \texttt{strtok} no es segura en entornos multihilo, por lo que se utiliza su variante \texttt{strtok\_r}.}.
    Se exige exactamente 12 columnas, descartando líneas incompletas o corruptas.
    Asimismo, se filtran valores literales \textit{null} y se aplican restricciones físicas (por ejemplo, color \(0.3 \leq B\!-\!V \leq 2.0\)).
    La conversión numérica se realiza con \texttt{strtod}/\texttt{strtof}/\texttt{strtoul}.

    \item \textbf{Gestión dinámica de memoria:}
    Cada hilo almacena temporalmente sus resultados en una estructura local \texttt{Star}.
    Debido a que no se conoce el número de estrellas que se van a leer, esta estructura se le asigna una capacidad inicial \texttt{capacity} de 10000 estrellas.
    Cuando el número de entradas supera la capacidad asignada, se amplía dinámicamente mediante \texttt{resize\_stars}.
    Finalizado el procesado de cada archivo, los datos locales se incorporan a la estructura global mediante una región crítica del menor tamaño posible (incrementar la capacidad del array global), manteniendo el resto de operaciones (copia de datos) fuera de ella para reducir contención.

    \item \textbf{Compactación final:}
    Una vez procesados todos los archivos, se ajusta la capacidad de la estructura global al número final de estrellas, liberando memoria no utilizada.
\end{enumerate}

En cuanto a la escritura y almacenamiento de datos, el sistema de salida ha sido rediseñado para utilizar el estándar \textbf{HDF5}, sustituyendo la escritura plana por un formato jerárquico binario que optimiza el espacio y facilita el acceso aleatorio a los datos.
El proceso se divide en las siguientes etapas:

\begin{enumerate}
    \item \textbf{Gestión de la estructura de directorios:}
    Para cada paso de tiempo (\texttt{step}) guardado se genera un subdirectorio independiente.
    Esto evita la saturación del sistema de archivos cuando se generan miles de ficheros a lo largo de la simulación.

    \item \textbf{Descomposición de dominio y balanceo de carga:}
    El vector global de estrellas se divide lógicamente en \(N\) fragmentos o \textit{chunks}.
    El tamaño de cada \textit{chunk} se calcula dinámicamente para repartir el remanente de estrellas, garantizando que todos los hilos de escritura procesen una carga de trabajo equilibrada.

    \item \textbf{Escritura paralela de archivos HDF5 (File-per-chunk):}
    Se emplea una estrategia de paralelización mediante \textbf{OpenMP}, donde cada hilo es responsable de crear y escribir un archivo HDF5 independiente (\texttt{.h5}).
    \begin{itemize}
        \item Se utilizan tipos de datos nativos de HDF5 (\texttt{H5T\_NATIVE\_FLOAT} para masa, \texttt{H5T\_NATIVE\_DOUBLE} para coordenadas y \texttt{H5T\_NATIVE\_UINT64} para identificadores), lo que garantiza la portabilidad binaria entre diferentes arquitecturas.
        \item Esta estrategia elimina la contención y el bloqueo de archivos (\textit{file locking}), permitiendo aprovechar el ancho de banda agregado del sistema de archivos paralelo (Lustre) del supercomputador.
    \end{itemize}

    \item \textbf{Interoperabilidad y Visualización (XDMF):}
    Finalmente, se genera un archivo descriptor \textbf{XDMF} (eXtensible Data Model and Format).
    Este archivo XML no contiene datos, sino que describe la topología de la nube de puntos y apunta a los datasets internos de los archivos HDF5. Esto permite que herramientas de visualización científica como \textit{ParaView} carguen los \(N\) archivos dispersos como un único objeto, simplificando drásticamente el post-procesado.
\end{enumerate}

\subsection{Construcción del árbol Barnes-Hut en CPU}\label{subsec:version-cpu}
El primer paso de la construcción del octree es elegir dónde colocar el nodo raíz y qué espacio ha de abarcar.
Este paso es crucial puesto que el posicionamiento del nodo raíz condiciona directamente las siguientes características:
\begin{itemize}
    \item Tamaño global del árbol: Puede requerirse la creación de más nodos internos para llegar a las mismas hojas.
    \item Balanceo de las ramas: Si muchas estrellas caen en el mismo octante frente a una distribución equitativa, puede quedar desbalanceado el árbol.
    \item Precisión de los cálculos: Al limitar el tamaño mínimo de un nodo, puede que un nodo hoja contenga más estrellas de las que debería.
\end{itemize}
La función \texttt{compute\_root\_bounds} realiza el cálculo del nodo raíz así como el tamaño mínimo de nodo en cuatro fases:
\begin{enumerate}
    \item \textbf{Cálculo del centro de masa global:}
    El objetivo inicial es determinar un punto representativo alrededor del cual construir el nodo raíz.
    Para ello se recorre el conjunto de estrellas acumulando su masa y su contribución ponderada a las coordenadas del centro de la siguiente forma:
    \begin{itemize}
        \item Se inicializan tres acumuladores (\texttt{center\_x}, \texttt{center\_y}, \texttt{center\_z}) y una suma total de masa (\texttt{total\_mass}).
        \item Para cada estrella:
        \begin{enumerate}
            \item Se añade su masa a \texttt{total\_mass}.
            \item Se acumula su posición multiplicada por la masa en cada coordenada.
        \end{enumerate}
        \item Tras recorrer cada coordenada acumulada se divide entre \texttt{total\_mass}, obteniendo el centro de masa.
    \end{itemize}

    Este proceso se paraleliza con \texttt{OpenMP} mediante una distribución estática de las iteraciones entre los hilos y reducción, ya que cada actualización de los acumuladores es independiente entre sí.
    \begin{lstlisting}[language=C, basicstyle=\ttfamily\small,label={lst:lstlisting5}]
#pragma omp parallel for reduction(+:total_mass,center_x,center_y,center_z)
    \end{lstlisting}
    \item \textbf{Obtención del radio inicial contenedor:}
    Una vez calculado el centro de masa, es necesario estimar el tamaño mínimo del cubo que contendrá a todas las estrellas.
    Para ello:
    \begin{itemize}
        \item Se recorre de nuevo el conjunto de estrellas y se mide la distancia de cada una al centro de masa.
        \item Se conserva únicamente la distancia máxima encontrada, lo que equivale al radio de la esfera más pequeña que cubre el sistema.
    \end{itemize}

    La búsqueda de la distancia máxima también se paraleliza mediante \texttt{OpenMP} con reducción \texttt{max}, aprovechando que cada comparación es independiente de las demás.
    \item \textbf{Refinamiento mediante expansión tipo Ritter:}
    Para evitar que la esfera inicial quede sobredimensionada por la presencia de estrellas aisladas, se aplica una actualización correctiva: si se detecta una estrella fuera de la esfera, el centro y el radio se ajustan para mantener la contención minimizando el volumen.
    Este proceso mejora la compacidad del nodo raíz y reduce el número de subdivisiones posteriores.
    Dicha implementación se ejecuta de forma estrictamente secuencial debido a la dependencia de datos crítica entre una iteración y la anterior, adicionalmente, para evitar la saturación del ancho de banda de memoria al recorrer $N \approx 10^9$ cuerpos, se aplica un submuestreo heurístico procesando únicamente una de cada ocho estrellas (\texttt{stride = 8}), asumiendo estadísticamente que este subconjunto (12.5\%) es suficiente para aproximar la envolvente convexa global sin incurrir en la penalización temporal de un recorrido completo.
    \item \textbf{Conversión a cubo y fijación de la escala mínima de subdivisión:}
    Finalmente, el radio obtenido se transforma en el \emph{half-size} del cubo raíz:
    \[
        h_s = 1.1 \, R,
    \]
    añadiendo un margen del $10\%$ para amortiguar errores de redondeo.

    El parámetro \texttt{min\_node\_size} se determina como:
    \[
        \text{min\_node\_size} = \frac{h_s}{\text{min\_subdivisions}},
    \]
    siendo \texttt{min\_subdivisions} un parámetro seleccionado por el usuario.
\end{enumerate}
El parámetro \texttt{min\_node\_size} limita la profundidad del árbol y define la resolución física mínima del modelo.
Cuando un nodo alcanza este tamaño, se deshabilita la subdivisión y se permite que múltiples estrellas coexistan en el mismo nodo.
Esto:
\begin{itemize}
    \item Previene subdivisiones infinitas en regiones densas.
    \item Reduce el coste computacional.
    \item Evita inestabilidades numéricas debidas a separación extremadamente pequeña.
\end{itemize}

Una vez seleccionado el nodo raíz, se insertan secuencialmente las estrellas tal y como se muestra en el Listing~\ref{lst:octree_insert}.
Para cada estrella se realiza una inserción recursiva:
\begin{enumerate}
    \item Se actualiza la \textbf{masa total} del nodo y su \textbf{centro de masa acumulado}.
    \item Si el nodo aún no contiene subdivisiones y su tamaño es mayor que el tamaño mínimo de nodo (\texttt{min\_node\_size}), se decide en qué octante cae la estrella usando:
    \[
        \mathrm{octante} =
        (\ x > c_x\ ) \cdot 4 +
        (\ y > c_y\ ) \cdot 2 +
        (\ z > c_z\ ) \cdot 1
    \]
    \item Si el nodo hijo correspondiente no existe, se crea con \texttt{octree\_new\_node}.
    \item Si el hijo ya contenía una estrella, entonces:
    \begin{itemize}
        \item Se marca como nodo interno.
        \item Se reinserta tanto la estrella ya almacenada como la nueva.
    \end{itemize}
\end{enumerate}
\begin{lstlisting}[
    language=pseudocode,
    caption={Algoritmo de inserción recursiva de una estrella en el Octree},
    label={lst:octree_insert}
]
// Función para organizar las estrellas jerárquicamente en el árbol
OCTREE_INSERT(tree, stars, n, s, min_node_size)
    // 1. Obtener datos geométricos del nodo n y físicos de la estrella s
    (cx, cy, cz, hs) <- obtener_geometria(n)
    (x, y, z, m)     <- obtener_datos_estrella(s)

    // 2. Actualización de propiedades físicas acumuladas del nodo
    old_mass <- tree.mass[n]
    new_mass <- old_mass + m
    tree.mass[n] <- new_mass
    // Cálculo del centro de masas mediante media ponderada
    tree.com[n]  <- (tree.com[n] * old_mass + (x,y,z) * m) / new_mass

    // 3. Control de granularidad: evitar subdivisiones infinitas
    SI (2 * hs <= min_node_size) ENTONCES
        SI tree.star_index[n] == VACIO ENTONCES
            tree.star_index[n] <- s
        FIN SI
        retornar
    FIN SI

    // 4. Determinar en cuál de los 8 octantes cae la estrella
    oct <- GET_OCTANT(cx, cy, cz, x, y, z)

    // 5. Gestión del nodo hijo correspondiente
    SI tree.children[n][oct] == INVALIDO ENTONCES
        // Caso: El octante esta vacío. Creamos nodo hoja.
        child <- CREAR_NODO(tree, calcular_centro(cx,cy,cz,hs,oct), hs/2)
        tree.children[n][oct]  <- child
        tree.star_index[child] <- s
        tree.mass[child]       <- m
        tree.com[child]        <- (x,y,z)
        retornar
    SINO
        child <- tree.children[n][oct]
        // Caso: El octante ya contiene una estrella. Subdividir.
        SI tree.star_index[child] != VACIO ENTONCES
            s_existente <- tree.star_index[child]
            tree.star_index[child] <- VACIO
            tree.mass[child] <- 0
            tree.com[child]  <- (0,0,0)
            // Reinsertar la estrella previa en el nuevo subnivel
            OCTREE_INSERT(tree, stars, child, s_existente, min_node_size)
        FIN SI

        // Insertar la nueva estrella s en el subárbol
        OCTREE_INSERT(tree, stars, child, s, min_node_size)
    FIN SI
\end{lstlisting}

\subsection{Construcción del árbol Barnes-Hut en GPU}\label{subsec:construccion-del-arbol-barnes-hut-en-gpu}

La versión del árbol para GPU presenta diferencias relevantes en la organización de datos y en el esquema de paralelización.

A pesar de que se sigue construyendo en CPU, la principal divergencia radica en el proceso de construcción del árbol.
Mientras que en CPU la inserción se realiza de forma secuencial, en la versión para GPU se paraleliza \textit{a nivel de octante}: cada uno de los ocho octantes principales del nodo raíz se construye de manera independiente.
Esto es posible porque, antes de la generación del árbol, las estrellas se reorganizan en memoria agrupándolas por octante.
Dado que el tamaño de los catálogos analizados en este trabajo es grande, resulta esencial evitar duplicaciones de memoria.
Por ello, la clasificación se realiza mediante un ordenamiento \textit{in-place}, lo que permite reestructurar el arreglo de estrellas sin necesidad de utilizar buffers adicionales.
El procedimiento es el siguiente:
\begin{enumerate}
    \item Se cuenta cuántas estrellas pertenecen a cada uno de los ocho octantes del nodo raíz.
    \item A partir de esos conteos se calculan desplazamientos (\textit{offsets}) que delimitan las regiones del arreglo destinadas a cada octante.
    \item Se reordenan las estrellas mediante intercambios internos (\texttt{swap}) de forma que los datos de cada octante queden almacenados de forma contigua en el mismo arreglo.
\end{enumerate}

Una vez completada esta reorganización, cada octante puede ser construido por un hilo de OpenMP independiente, ya que cada uno escribe únicamente dentro de su propia subregión de memoria.
Como consecuencia, la construcción del árbol resulta \textbf{paralela y libre de bloqueos}, sin necesidad de sincronización entre octantes.
El octree resultante es equivalente al obtenido en CPU, manteniendo el mismo número de nodos y la misma estructura geométrica.

Además, tras la construcción del árbol, se generan los \textit{ropes} (punteros laterales entre nodos vecinos), cuyo propósito es permitir el recorrido del árbol sin recurrencia.
Cada nodo almacena un puntero al siguiente nodo que debe visitarse cuando se ha terminado de procesar su subárbol.
De este modo, la navegación del árbol se convierte en un recorrido iterativo eficiente, particularmente adecuado para GPU, donde la recursión está limitada o directamente prohibida.

La construcción de los \textit{ropes} se realiza mediante un recorrido estructural sobre el árbol ya construido, tal y como se muestra en el Listing~\ref{lst:ropes}.
\begin{lstlisting}[
    language=pseudocode,
    caption={Algoritmo de construcción de \textit{ropes} (punteros laterales) en el Octree},
    label={lst:ropes}
]
// Función recursiva para enlazar nodos y permitir recorrido stackless
BUILD_ROPES(node, next)
    SI node == NULL ENTONCES
        retornar
    FIN SI

    // El puntero 'next' apunta al siguiente nodo fuera del subárbol actual
    node.next <- next

    // Procesar los 8 hijos para establecer sus conexiones laterales
    para i = 0 .. 7 HACER
        child <- node.child[i]

        si child != NULL ENTONCES
            // El 'next' del hijo es el primer hermano válido a su derecha
            child_next <- buscar_siguiente_hermano_valido(node, i)

            // Si es el último hijo, hereda el 'next' de su padre
            si child_next == NULL ENTONCES
                child_next <- next
            fin si

            // Llamada recursiva
            BUILD_ROPES(child, child_next)
        fin si
    FIN HACER
\end{lstlisting}
Además de la construcción paralela de los octantes, es necesario reintroducir la \textbf{influencia gravitacional entre los mismos}.
Al haber separado la distribución original de estrellas en ocho regiones independientes, cada octree parcial contiene solo información local y, por tanto, no puede por sí solo estimar la contribución gravitatoria del resto del sistema. Para resolver esto, se construye una \textbf{frontera gravitacional} (\textit{frontier}), que actúa como un conjunto compacto de masas equivalentes que representan a los demás octantes externos.
El procedimiento funciona de la siguiente manera:
\begin{enumerate}
    \item Para un octante concreto, se recorre el árbol correspondiente a cada uno de los otros siete octantes.
    \item En cada nodo visitado, se aplica el \textbf{criterio de aproximación Barnes--Hut}:
    \[
        \frac{s}{d} < \theta,
    \]
    donde $s$ es el tamaño del nodo y $d$ la distancia al centro del octante destino.
    \begin{itemize}
        \item Si la condición se cumple, el nodo se \textbf{acepta como una única partícula equivalente}, caracterizada por su masa total y centro de masa.
        \item Si la condición no se cumple, se \textbf{desciende recursivamente} a los hijos del nodo para obtener una representación más fina.
    \end{itemize}
    \item Los nodos aceptados se almacenan en una estructura llamada \texttt{FrontierGPU}, que contiene exclusivamente las masas efectivas necesarias para ese octante.
\end{enumerate}

Este proceso genera, para cada octante, una lista comprimida de fuentes gravitacionales externas, de tamaño reducido en comparación con el árbol completo.
Durante la fase de cómputo de aceleraciones en GPU, cada bloque solo necesita acceder a su propio subárbol y frontera asociada.
De esta forma se evita la necesidad de:
\begin{itemize}
    \item Compartir nodos globales entre bloques.
    \item Realizar sincronización entre octantes.
    \item Introducir bloqueos que degraden el rendimiento.
    \item Almacenar el árbol completo en cada GPU.
\end{itemize}

El resultado es una versión completamente paralelizable del método de Barnes--Hut que mantiene la misma aproximación física estándar, pero adaptada para arquitecturas masivamente paralelas.

\subsection{Simulación en CPU}\label{subsec:simulacion-cpu}
Una vez construido el árbol, podemos computar las aceleraciones utilizando el algoritmo de Barnes-Hut y actualizar las posiciones y las velocidades utilizando el esquema de integración temporal KDK mencionado en la sección~\ref{subsec:esquema-de-integracion-temporal-(leapfrog-kick--drift--kick).}.

\subsubsection{Cálculo de aceleraciones Barnes--Hut}
El núcleo del cálculo de fuerzas es la función \texttt{compute\_acceleration\_bh}, que realiza un recorrido del árbol adaptativo para estimar la contribución gravitatoria sobre una estrella dada.
La función recibe un nodo del árbol y decide si:
\begin{enumerate}
    \item Tratarlo como una \emph{masa efectiva única} (si cumple el criterio de apertura Barnes--Hut).
    \item Descender recursivamente a sus hijos para obtener una aproximación más detallada.
\end{enumerate}

El criterio se evalúa comparando la relación entre el tamaño del nodo y la distancia:
\[
    \frac{s}{d} < \theta,
\]
donde $s$ es el lado del nodo y $d$ la distancia entre el centro de masa del nodo y la estrella objetivo.
Si además el nodo contiene sólo una partícula, se toma siempre como masa puntual.

Entre las optimizaciones más relevantes se incluyen: las operaciones de acumulación se realizan usando \texttt{fma} para evitar pérdidas numéricas y Se descarta explícitamente el caso donde la estrella es la misma que la contenida en el nodo hoja.

El cálculo de aceleraciones es independiente para cada estrella, por lo que se paraleliza en un bucle OpenMP.
Cada hilo realiza recorridos independientes sobre el mismo árbol, que permanece en memoria de solo lectura durante esta fase.
Por tanto, la paralelización es completamente \textbf{libre de bloqueos}.

El bucle de integración temporal realiza:
\begin{enumerate}
    \item \textbf{Half-Kick:} Se actualizan las velocidades usando las aceleraciones actuales.
    \item \textbf{Drift:} Se actualizan las posiciones.
    \item \textbf{Reconstrucción del árbol:} Las posiciones han cambiado, por lo que la estructura espacial debe actualizarse.
    El árbol anterior se libera y se vuelve a construir usando la función \texttt{build\_tree}.
    \item \textbf{Re-cálculo de aceleraciones:} Se evalúan nuevamente las fuerzas usando el nuevo árbol.
    \item \textbf{Half-Kick final:} Se completan las velocidades del paso.
\end{enumerate}

\subsubsection{Reutilización de memoria y eficiencia}
La reconstrucción del árbol en cada paso temporal resulta imperativa, dado que el desplazamiento significativo de las estrellas altera la distribución espacial de la que dependen tanto la precisión como el rendimiento del algoritmo Barnes-Hut.

Con el objetivo de minimizar la sobrecarga computacional asociada a este proceso recurrente, se han adoptado estrategias de gestión eficiente de recursos.
En primer lugar, se evita la latencia de asignación continua mediante la reserva única y persistente de los arrays de aceleraciones (\texttt{ax}, \texttt{ay}, \texttt{az}), los cuales son reutilizados en cada iteración.
De forma complementaria, la gestión de memoria para la estructura del árbol emplea un mecanismo de \textit{realocación progresiva} —análogo al utilizado durante la carga inicial de datos— que permite ajustar dinámicamente la capacidad reservada al número fluctuante de nodos requeridos.
Finalmente, para maximizar el rendimiento del sistema, todas las etapas susceptibles de ejecución concurrente, tales como el cálculo de interacciones gravitatorias y la actualización de los estados cinemáticos, se procesan en paralelo bajo directivas \texttt{omp parallel for}.

\subsection{Simulación en GPU}\label{subsec:simulacion-gpu}

La versión en GPU mantiene el mismo esquema de integración temporal que la versión en CPU, pero reestructura la organización de datos y el recorrido del árbol para explotar el paralelismo masivo de las GPUs y minimizar transferencias de memoria.
La simulación se ejecuta distribuyendo los octantes principales del árbol entre múltiples GPUs, de forma que cada dispositivo procesa únicamente las estrellas contenidas en su región espacial correspondiente.

Antes de cada paso se ejecuta la función \texttt{reorder\_stars}, que reordena las estrellas de acuerdo al octante del espacio que ocupan con respecto a la raíz del árbol.
Esto produce:
\begin{itemize}
    \item Particiones contiguas en memoria con estrellas espacialmente cercanas.
    \item Coalescencia en accesos a memoria en GPU.
    \item La posibilidad de asignar cada octante a una GPU diferente sin necesidad de copias de subconjuntos dispersos.
\end{itemize}

El número de GPUs disponibles define cuántos octantes se procesan de manera simultánea.
Para un total de ocho octantes, el número de iteraciones de cálculo es:
\[
    \texttt{iterations} = \left\lceil \frac{8}{\texttt{device\_count}} \right\rceil.
\]

El árbol Barnes--Hut no se recorre recursivamente en GPU, ya que la recursión implicaría un uso intensivo de memoria local y divergencia de hilos.
En su lugar se usa: un \textbf{árbol lineal} almacenado en memoria global, nodos con punteros a hijos directos y un puntero \texttt{next} (\emph{rope}) por nodo que permite avanzar al siguiente nodo relevante sin volver a la raíz.

Este esquema de navegación permite un recorrido del árbol totalmente \emph{stackless} (sin pila), lo que resulta crítico en arquitecturas GPU para eliminar el desbordamiento de memoria local y minimizar la divergencia entre hilos de un mismo \texttt{warp}.
El flujo lógico se resume en el algoritmo del Listing~\ref{lst:gpu_stackless}:

\begin{lstlisting}[
    language=pseudocode,
    caption={Algoritmo de recorrido del árbol Barnes-Hut en GPU (Stackless)},
    label={lst:gpu_stackless}
]
// Inicialización: el hilo comienza en la raíz
node <- root

MIENTRAS node != INVALID HACER
    ratio <- s / d

    SI ratio < theta ENTONCES
        // Caso A: Aproximación multipolar
        aceleracion += calcular_masa_puntual(node)
        node <- node.next
    SINO SI es_hoja(node) ENTONCES
        // Caso B: Interacción directa
        aceleracion += calcular_interaccion_directa(node)
        node <- node.next
    SINO
        // Caso C: Descenso al hijo
        node <- primer_hijo(node)
    FIN SI
FIN MIENTRAS
\end{lstlisting}

Gracias al uso de punteros \texttt{next} (o \emph{ropes}), cuando un hilo decide que un nodo es lo suficientemente lejano para aplicar la aproximación de Barnes--Hut, puede omitir todo el subárbol descendiente de forma inmediata.
De igual modo, tras procesar una hoja, el puntero \texttt{next} conduce directamente al siguiente nodo relevante en el orden de visita, transformando una búsqueda recursiva compleja en un recorrido lineal eficiente.

Para aumentar la eficiencia en la GPU se toman las siguientes decisiones clave de implementación:
\begin{itemize}
    \item Los nodos se almacenan como estructuras contiguas en memoria global, favoreciendo el acceso coalescente al recorrer el árbol.
    \item El uso del campo \texttt{next} evita tanto la recursión como el uso de pilas auxiliares en memoria local o compartida.
    \item Los cálculos usan operaciones \texttt{fma} (fused multiply-add) para combinar precisión numérica y rendimiento.
    \item Se evita cualquier rama condicional dependiente del hilo, reduciendo la divergencia de \texttt{warp} en nodos cercanos a los criterios de apertura.
    \item Para cada octante se precomputa en CPU una \textbf{frontera lineal} que contiene nodos distantes que ya se sabe que cumplen el criterio de apertura.
    Esta frontera se transfiere a la GPU junto con el árbol reducido del octante.
    De esta forma se evita trabajo redundante y la GPU no decide qué nodos de niveles superiores incluir.
    La frontera se construye tras separar los octantes, para que cada GPU trabaje solo con la información relevante a su volumen espacial y se almacena como un arreglo lineal, facilitando su recorrido en un único bucle sin ramificaciones.
\end{itemize}

\subsubsection{Kernel de fuerzas en GPU}

La implementación del cálculo de aceleraciones en la GPU se basa en el kernel principal \texttt{compute\_forces\_kernel}, donde cada hilo de ejecución procesa una única estrella.
El flujo de control dentro del kernel se ha diseñado para minimizar la latencia y maximizar el rendimiento mediante las siguientes etapas:

\begin{enumerate}
    \item \textbf{Inicialización:} Se declaran los acumuladores de aceleración local directamente en los registros del hilo para garantizar un acceso de alta velocidad.
    \item \textbf{Potenciales analíticos:} Se calculan y aplican de forma directa las contribuciones del potencial del halo (NFW) y del bulbo (Hernquist) aprovechando las unidades de cómputo del dispositivo.
    \item \textbf{Recorrido del árbol local:} El hilo navega por el subárbol del octante correspondiente utilizando el método \textit{stackless} mediante \textit{ropes}. Esta técnica sustituye la recursividad por una iteración directa sobre punteros laterales, optimizando el uso de la memoria local.
    \item \textbf{Procesamiento de la frontera:} Se recorre la frontera lineal prefiltrada que contiene la representación multipolar compacta del resto de los octantes del sistema.
    \item \textbf{Integración cinemática:} Se actualiza la velocidad de la estrella aplicando el semipaso (\textit{kick}) mediante la constante \texttt{c\_dt2}.
    \item \textbf{Actualización de posición:} En la primera mitad del paso temporal, se aplica opcionalmente la fase de \textit{drift}.
\end{enumerate}

Para alcanzar una alta eficiencia en la arquitectura CUDA, se han integrado las siguientes decisiones de diseño:
\begin{itemize}
    \item \textbf{Jerarquía de memoria:} Las variables globales de simulación (\texttt{c\_dt}, \texttt{c\_theta2}, etc.) se almacenan en \textbf{memoria constante}. Las posiciones y velocidades se mantienen en memoria global, pero organizadas para permitir accesos \textbf{coalescentes} por parte de los \textit{warps}.
    \item \textbf{Eficiencia de tráfico:} Las aceleraciones calculadas no se almacenan de forma intermedia en memoria global; se aplican inmediatamente a los registros de velocidad y posición, reduciendo drásticamente el tráfico de datos.
    \item \textbf{Funciones intrínsecas:} Se utiliza explícitamente \texttt{rsqrt()} para el cálculo de distancias, proporcionando una velocidad superior con la precisión necesaria para la dinámica estelar.
\end{itemize}

El sistema escala a múltiples dispositivos mediante una distribución de carga basada en octantes.
Para cada GPU presente en el sistema, se sigue un procedimiento coordinado por hilos de OpenMP:

\begin{enumerate}
    \item \textbf{Carga de datos:} Se transfieren las posiciones y velocidades correspondientes al rango de estrellas asignado al dispositivo.
    \item \textbf{Estructuras jerárquicas:} Se copian el subárbol local y su frontera multipolar asociada.
    \item \textbf{Lanzamiento asíncrono:} Se invoca el kernel en un \texttt{cudaStream} independiente. El uso de \texttt{cudaMemcpyAsync} permite solapar las transferencias con el cómputo del kernel.
    \item \textbf{Recuperación de resultados:} Tras la ejecución, se copian de vuelta al \textit{host} las velocidades actualizadas y, si el paso lo requiere, las nuevas posiciones.
\end{enumerate}

Para evitar tiempos muertos de comunicación, las GPUs se sincronizan únicamente al final de cada fase de integración.
Además, se emplea una política de \textbf{copiar-construir-liberar} para los árboles y fronteras en cada medio paso, lo que garantiza la consistencia de la simulación independientemente de los reordenamientos internos de las estrellas. La coordinación de este pipeline híbrido CUDA+OpenMP se centraliza en la función \texttt{compute\_halfstep}, asegurando una ejecución paralela libre de interferencias.

\section{Arquitectura del sistema y flujo de datos}\label{sec:arquitectura}
El software desarrollado está públicamente disponible en el repositorio de GitHub: \url{https://github.com/Anse1000/TFG_PabloRey.git}
El sistema engloba las versiones CPU y GPU del simulador de dinámica galáctica.
Ambas versiones tienen una arquitectura modular y comparten la misma interfaz de entrada/salida, las mismas estructuras de datos fundamentales y el mismo pipeline de procesamiento, permitiendo una fácil validación cruzada de resultados y comparación de rendimiento.
La selección entre la versión CPU o GPU se realiza en tiempo de compilación mediante opciones de CMake (\texttt{ENABLE\_CUDA}), facilitando la adaptación a distintas infraestructuras y volumen de datos.
A continuación se detalla la estructura de los archivos principales, divididos según su ubicación en el árbol de directorios:

\paragraph*{Núcleo del sistema (\texttt{src/})}
Este directorio contiene los puntos de entrada y las utilidades compartidas por ambas implementaciones (CPU y GPU).

\begin{itemize}
    \item \texttt{main.c}: Punto de entrada de la aplicación. Gestiona el análisis de argumentos de línea de comandos, inicializa la configuración global y orquesta la selección entre la simulación en CPU o GPU.
    \item \texttt{types.h}: Archivo de cabecera central que define las constantes físicas, parámetros galácticos y las estructuras de datos fundamentales (como \texttt{Star}) utilizadas en todo el proyecto.
    \item \texttt{file\_handler.c/h}: Módulo encargado de la capa de persistencia. Implementa la lectura paralela y eficiente de archivos CSV y gestiona la escritura de resultados en formato jerárquico HDF5 y descriptores XDMF.
    \item \texttt{calculations.c/h}: Biblioteca de funciones matemáticas y físicas compartidas, incluyendo transformaciones de coordenadas y cálculos vectoriales básicos.
    \item \texttt{aux\_fun.c/h}: Colección de utilidades para la medición de tiempos de ejecución, manejo de cadenas y gestión de errores.
\end{itemize}

\paragraph*{Módulo CPU (\texttt{src/cpu/})}
Contiene la implementación de la simulación basada en procesadores convencionales utilizando OpenMP.

\begin{itemize}
    \item \texttt{octree\_cpu.c/h}: Implementa la estructura de datos del árbol octal (\textit{Octree}) y los algoritmos recursivos para su construcción y recorrido según el método de Barnes-Hut estándar.
    \item \texttt{simulation.c/h}: Define el bucle principal de integración temporal para la versión CPU, coordinando los pasos de \textit{kick} y \textit{drift} y la reconstrucción del árbol en cada iteración.
\end{itemize}

\paragraph*{Módulo GPU (\texttt{src/gpu/})}
Contiene la lógica específica para la aceleración mediante GPU NVIDIA y CUDA.

\begin{itemize}
    \item \texttt{cuda\_functions.cu/cuh}: Archivos que contienen los \textit{kernels} CUDA (.cu) que se ejecutan en el dispositivo. Gestionan el cálculo masivo de fuerzas, la actualización de posiciones y la transferencia de memoria entre \textit{host} y \textit{device}.
    \item \texttt{octree\_gpu.c/h}: Gestiona la adaptación del árbol octal para la GPU. Se encarga de la lógica del \textit{host} para preparar las estructuras lineales y las fronteras (\textit{frontiers}) que consumirán los kernels.
\end{itemize}

\paragraph*{Scripts y herramientas (\texttt{scripts/})}
El directorio \texttt{scripts} alberga herramientas auxiliares desarrolladas en Python y Bash para el preprocesamiento y postprocesamiento.

\begin{itemize}
    \item \textbf{Gestión de datos:} Scripts que automatizan la descarga de catálogos desde Gaia y TAPVizieR, así como su limpieza y fusión en archivos CSV optimizados.
    \item \textbf{Ejecución HPC:} Archivos con extensión \texttt{.slurm} que definen los trabajos por lotes para el gestor de colas del supercomputador.
    \item \textbf{Visualización:} \texttt{render.py} permite generar representaciones gráficas rápidas de la simulación para validación visual.
\end{itemize}
