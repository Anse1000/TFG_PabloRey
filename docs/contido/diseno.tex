\chapter{Diseño e implementación}
\label{chap:diseno}
En este capítulo se describe la arquitectura del sistema, las estructuras de datos, los algoritmos principales y las decisiones de implementación que sustentan el proyecto, desde la ingesta de datos hasta la simulación y la generación de salidas.
\section{Obtención y preparación de los datos}\label{sec:datos}

Para realizar la simulación fue necesario disponer de varios subconjuntos de datos procedentes del catálogo \textit{Gaia DR3} y del catálogo complementario de distancias \texttt{GeDR3Dist}.
El proceso completo comprendió la descarga, reducción y combinación de los distintos catálogos, con el objetivo de obtener un conjunto coherente de parámetros espaciales, fotométricos y físicos.

\subsection*{Descarga de los catálogos principales}

Los catálogos \texttt{gaia\_source} y \texttt{astrophysical\_parameters} se descargaron desde el \textit{Gaia Archive}~\cite{gaia_archive} mediante el comando \texttt{wget}, automatizando la obtención de archivos comprimidos en formato \texttt{.csv.gz}:

\begin{verbatim}
wget -r -np -nd -A "*.csv.gz" "URL_archivos"
\end{verbatim}

Cada archivo contiene un subconjunto del catálogo particionado por rangos de \texttt{source\_id}, lo que facilita la descarga y el procesamiento distribuido.
El tamaño total de la descarga es de aproximadamente 757~GB para la tabla \texttt{gaia\_source} y 258~GB para \texttt{astrophysical\_parameters}, sumando un total de 3\,386 archivos en cada caso.
\subsection*{Descarga del catálogo de distancias}

Las estimaciones de distancia derivadas del paralaje se obtuvieron a partir del catálogo \texttt{I/352/GeDR3Dist}, disponible a través del servicio \textit{TAPVizieR}.
Dado el volumen de datos (más de mil millones de fuentes), se diseñó un script en \texttt{bash}~\ref{lst:script_descargar_distances} que divide el rango de \texttt{source\_id} en bloques y realiza consultas ADQL (\textit{Astronomical Data Query Language}) sucesivas al servidor.

De esta forma se obtuvieron diversos archivos \texttt{.csv} con los campos \texttt{Source} y \texttt{rgeo}, que posteriormente se integraron en el conjunto de datos principal.
\subsection*{Reducción de columnas}

Con el fin de optimizar el almacenamiento y acelerar las operaciones de lectura, los archivos originales se redujeron manteniendo únicamente las columnas relevantes para el análisis:
\texttt{source\_id}, \texttt{ra}, \texttt{dec}, \texttt{pmra}, \texttt{pmdec}, \texttt{radial\_velocity}, \texttt{phot\_g\_mean\_mag} y \texttt{bp\_rp}.
El filtrado se realizó mediante herramientas de línea de comandos (\texttt{awk}) y utilizando \texttt{parallel} para acelerar el proceso, generando versiones compactas de los catálogos~\ref{lst:script_reducir_astro}.
\subsection*{Combinación de catálogos}

Finalmente, los catálogos reducidos de \texttt{gaia\_source}, \texttt{astrophysical\_parameters} y \texttt{GeDR3Dist} se combinaron utilizando un script en \texttt{Python}~\ref{lst:script_combinar} con las librerías \texttt{pandas} y \texttt{duckdb}.
Primero se creó una base de datos temporal con las distancias debido al diferente número de archivos por tabla y el orden de IDs, y posteriormente se fusionaron los catálogos mediante uniones internas sobre el campo \texttt{source\_id}, aprovechando el procesamiento en paralelo para reducir el tiempo de ejecución:

\begin{verbatim}
merged = pd.merge(main_df, astro_df, on='source_id')
merged = pd.merge(merged, distance_df, on='source_id')
\end{verbatim}

El resultado final fue un conjunto de 3386 archivos optimizados \texttt{merged\_XXXX.csv}, listos para el filtrado y el análisis posterior ocupando 223~GB sin comprimir.

Este procedimiento permitió manejar de forma eficiente el volumen total del catálogo (más de 1\,800 millones de fuentes en \textit{Gaia DR3}), garantizando coherencia y consistencia entre todos los parámetros empleados.
\section{Arquitectura del sistema y flujo de datos}\label{sec:arquitectura}
El sistema implementa un simulador de dinámica galáctica mediante una arquitectura modular que soporta dos implementaciones complementarias: una versión \textbf{CPU}, basada en paralelización mediante OpenMP, y una versión \textbf{GPU}, que aprovecha la capacidad de cómputo masivo de aceleradores NVIDIA mediante CUDA\@.

Ambas versiones comparten la misma interfaz de entrada/salida, las mismas estructuras de datos fundamentales y el mismo pipeline de procesamiento, permitiendo una fácil validación cruzada de resultados y comparación de rendimiento.
La selección entre la versión CPU o GPU se realiza en tiempo de compilación mediante opciones de CMake (\texttt{ENABLE\_CUDA}), facilitando la adaptación a distintas infraestructuras y volumen de datos.

\section{Estructuras de datos principales}\label{sec:estructuras}
El sistema utiliza varias estructuras de datos fundamentales que son compartidas entre la versión CPU y GPU, además de otras especializadas en cada versión.
Estas estructuras están diseñadas para optimizar tanto el acceso a memoria como la compatibilidad con los modelos de paralelización disponibles.

\subsection{Estructura de estrella (\texttt{Star})}\label{subsec:estructura-de-estrella-(texttt{star})}

La estructura central del sistema es \texttt{Star}, que agrupa los parámetros astrométricos, cinemáticos y físicos de cada objeto celeste.
Esta estructura se organiza de forma \textit{structure-of-arrays} (SoA) en lugar de arrays de estructuras, permitiendo optimizar el acceso a memoria en operaciones paralelas y facilitar la vectorización automática en CPU y GPU.

\subsubsection*{Diseño y selección de tipos de datos}

La selección de tipos de datos en cada campo responde a criterios de precisión numérica y eficiencia de memoria:

\begin{itemize}
    \item \textbf{Precisión doble (\texttt{double}, 64 bits)}:
    \begin{itemize}
        \item \texttt{ra}, \texttt{dec}, \texttt{distance}, \texttt{pmra}, \texttt{pmdec}, \texttt{radial\_velocity}: Los datos originales de Gaia DR3 se proporcionan en precisión doble. Mantenerlos así preserva la precisión astrométrica y es necesario para transformaciones de coordenadas que acumulan errores.

        \item \texttt{Cx}, \texttt{Cy}, \texttt{Cz}, \texttt{Vx}, \texttt{Vy}, \texttt{Vz}: Las coordenadas cartesianas heliocéntricas y velocidades se mantienen en doble precisión para garantizar estabilidad numérica durante la integración temporal de órbitas a lo largo de millones de años. Los errores de redondeo en precisión simple acumularían desviaciones significativas en las trayectorias.
    \end{itemize}

    \item \textbf{Precisión simple (\texttt{float}, 32 bits)}:
    \begin{itemize}
        \item \texttt{mass}, \texttt{radius}, \texttt{gravity}, \texttt{mean\_g}, \texttt{color}: Estos parámetros representan propiedades físicas derivadas o fotométricas con precisión inherente limitada. La masa se estima mediante relaciones empíricas con incertidumbre del orden del 10--20\%. El índice de color y magnitud se proporcionan con precisión limitada en el catálogo. Usar precisión simple reduce el consumo de memoria a la mitad en estos campos sin pérdida práctica de información.
    \end{itemize}

    \item \textbf{Identificador de 64 bits sin signo (\texttt{unsigned long})}:
    \begin{itemize}
        \item \texttt{id}: Identificador único de Gaia DR3, necesario para relacionar datos con el catálogo original.
    \end{itemize}
\end{itemize}

\subsubsection*{Consumo de memoria}
Para una estructura con $N$ estrellas y capacidad $C$:
\[
    \text{Memoria} = C \times (8 + 8 \times 6 + 8 \times 3 + 8 \times 3 + 4 \times 5) \text{ bytes} = C \times 152 \text{ bytes}
\]

Esto es:
\begin{itemize}
    \item \texttt{id}: 8 bytes $\times$ 1 = 8 bytes
    \item \texttt{ra}, \texttt{dec}, \texttt{distance}, \texttt{pmra}, \texttt{pmdec}, \texttt{radial\_velocity}: 8 bytes $\times$ 6 = 48 bytes
    \item \texttt{Cx}, \texttt{Cy}, \texttt{Cz}, \texttt{Vx}, \texttt{Vy}, \texttt{Vz}: 8 bytes $\times$ 6 = 48 bytes
    \item \texttt{mean\_g}, \texttt{color}, \texttt{radius}, \texttt{gravity}, \texttt{mass}: 4 bytes $\times$ 5 = 20 bytes
    \item \textbf{Total por estrella: 152 bytes}
\end{itemize}

Para una simulación con 1.100 millones de estrellas utilizadas en el proyecto como se ve en la subsección~\ref{sec:filtrado}, la memoria requerida sería:

\[
    1.1 \times 10^9 \times 152 \text{ bytes} = 171.3 \text{ GB}
\]
tamaño perfectamente abarcable en los nodos disponibles en el Finisterrae III de 256 GB de RAM~\ref{subsec:especificaciones-tecnicas-de-los-nodos}.

\subsubsection*{Liberación selectiva de datos}

Tras la carga completa de un bloque de estrellas y la realización de los cálculos preliminares (transformación de coordenadas y estimación de masas), ciertos campos astrométricos originales dejan de ser necesarios y son liberados para reducir el consumo de memoria:

\begin{itemize}
    \item \textbf{Datos liberados después de transformación de coordenadas}:
    \begin{itemize}
        \item \texttt{ra}, \texttt{dec}, \texttt{distance}: Tras convertir a coordenadas cartesianas heliocéntricas (\texttt{Cx}, \texttt{Cy}, \texttt{Cz}), estos datos ecuatoriales ya no son necesarios.

        \item \texttt{pmra}, \texttt{pmdec}, \texttt{radial\_velocity}: Tras convertir a velocidades cartesianas (\texttt{Vx}, \texttt{Vy}, \texttt{Vz}), estos datos originales no vuelven a usarse.
    \end{itemize}

    \item \textbf{Datos liberados después de estimación de masas}:
    \begin{itemize}
        \item \texttt{gravity}, \texttt{mean\_g}, \texttt{color}: Tras estimar \texttt{mass} mediante la relación masa-luminosidad que utiliza estos parámetros, pueden ser liberados si no se requieren en resultados finales.
    \end{itemize}

    \item \textbf{Impacto en memoria}:
    Liberando los 6 campos astrométricos originales reduce el consumo en 48 bytes por objeto, correspondiendo a una reducción del 31.6\% respecto al consumo total por estrella.
    Para 1.100 millones de estrellas, esto libera aproximadamente 49.2 GB de memoria.
\end{itemize}

Este diseño permite un balance entre precisión numérica, eficiencia de memoria y adaptabilidad a diferentes infraestructuras y volúmenes de datos, siendo crucial para gestionar simulaciones de escala galáctica en entornos de computación de altas prestaciones.

\subsection{Estructura de arbol CPU(\texttt{Octree})}\label{subsec:estructura-de-arbol-cpu(texttt{octree})}

La estructura \texttt{Octree} implementa el árbol jerárquico utilizado en la versión CPU del simulador para acelerar el cálculo de fuerzas gravitatorias mediante el método de Barnes-Hut.
A diferencia de la estructura \texttt{Star}, que es plana y homogénea, el octree es una estructura (SoA) jerárquica donde cada nodo contiene referencias a hasta 8 nodos hijos.

\subsubsection*{Diseño y campos de datos}

Cada nodo del octree almacena información geométrica, propiedades físicas acumuladas e información topológica:

\begin{itemize}
    \item \textbf{Geometría del volumen (precisión simple, \texttt{float})}:
    \begin{itemize}
        \item \texttt{center\_x}, \texttt{center\_y}, \texttt{center\_z}: Coordenadas del centro del cubo (float, 3 $\times$ 4 = 12 bytes)

        \item \texttt{half\_size}: Semiextensión del cubo en cada dirección (float, 4 bytes)

        \textbf{Justificación de precisión simple}: La geometría del árbol se utiliza únicamente para aplicar el criterio de apertura de Barnes-Hut (comparación de distancias). La precisión simple es suficiente para estas comparaciones relativas sin afectar la validez del criterio de agrupación.
    \end{itemize}

    \item \textbf{Propiedades físicas (masa en \texttt{float}, centro de masas en \texttt{double})}:
    \begin{itemize}
        \item \texttt{mass}: Masa total acumulada del nodo y sus descendientes (float, 4 bytes)

        \item \texttt{com\_x}, \texttt{com\_y}, \texttt{com\_z}: Centro de masas (double, 3 $\times$ 8 = 24 bytes)

        \textbf{Justificación de precisión mixta}: La masa total se almacena en precisión simple ya que es el resultado de sumas acumulativas que se recomputabilizan en cada reconstrucción del árbol.
        El centro de masas, sin embargo, se mantiene en precisión doble porque:
        \begin{enumerate}
            \item Se utiliza directamente en el cálculo de la aceleración gravitatoria.
            \item Se actualiza mediante una operación de media ponderada que puede acumular errores significativos en precisión simple.
            \item La precisión en la localización del centro de masas afecta directamente a la exactitud de la aproximación multipolar.
        \end{enumerate}
    \end{itemize}

    \item \textbf{Información topológica}:
    \begin{itemize}
        \item \texttt{children}: Array de 8 referencias a nodos hijos (array de 8 enteros sin signo de 32 bits, 32 bytes).

        Se utiliza \texttt{unsigned int} en lugar de \texttt{long} por dos razones críticas:
        \begin{enumerate}
            \item \textbf{Ahorro de memoria}: Cada referencia ocupa 4 bytes en lugar de 8, reduciendo en un 50\% el espacio dedicado a punteros.

            \item \textbf{Límite máximo de nodos}: El rango de \texttt{unsigned int} es de 0 a $2^{32} - 1 = 4{,}294{,}967{,}295$, más que suficiente para los nodos esperados en una simulación de 1.100 millones de estrellas.
        \end{enumerate}

        La representación de sin hijo utiliza la constante \texttt{INVALID\_INDEX = UINT32\_MAX} (4.294 mil millones), un valor fuera del rango de nodos válidos.
        Aunque \texttt{unsigned int} no permite directamente valores negativos como -1, el uso de \texttt{UINT32\_MAX} es una estrategia estándar que proporciona semántica equivalente: una comparación \texttt{if (child == INVALID\_INDEX)} determina de forma unívoca si el hijo existe.

        \item \texttt{star\_index}: Índice de la estrella si el nodo es una hoja, o -1 si es un nodo interno (long, 8 bytes).

        Este campo mantiene precisión de 64 bits porque son los mismos valores que los almacenados en Star.
    \end{itemize}
\end{itemize}

\subsubsection*{Consumo de memoria}

Memoria por nodo del octree:

\[
    \text{Memoria por nodo} = 4 \times 4 + 4 + 24 + 32 + 8 = 88 \text{ bytes}
\]

Esto es:
\begin{itemize}
    \item \texttt{center\_x}, \texttt{center\_y}, \texttt{center\_z}, \texttt{half\_size}: 4 bytes $\times$ 4 = 16 bytes
    \item \texttt{mass}: 4 bytes
    \item \texttt{com\_x}, \texttt{com\_y}, \texttt{com\_z}: 8 bytes $\times$ 3 = 24 bytes
    \item \texttt{children[8]}: 4 bytes $\times$ 8 = 32 bytes
    \item \texttt{star\_index}: 8 bytes
    \item \textbf{Total por nodo: 88 bytes}
\end{itemize}

\subsection{Estructura de arbol GPU(\texttt{OctreeGPU})}\label{subsec:estructura-de-arbol-gpu(texttt{octreegpu})}
La estructura \texttt{OctreeGPU} implementa el árbol jerárquico para la versión acelerada por GPU\@.
Aunque mantiene la misma lógica algorítmica de Barnes-Hut que la versión CPU, su organización física es fundamentalmente diferente, optimizada para:
\begin{enumerate}
    \item Maximizar la coalesced memory access en GPU (acceso contiguo a memoria)
    \item Minimizar las divergencias de control entre threads CUDA
    \item Reducir la necesidad de sincronización global entre dispositivos
    \item Facilitar la paralelización masiva de búsquedas en el árbol
\end{enumerate}

En lugar de un único árbol monolítico como en CPU, la versión GPU divide el árbol raíz en 8 subárboles independientes, uno para cada octante del espacio:

\begin{lstlisting}[language=C,label=octree_gpu_struct,caption=Estructura OctreeGPU con partición en octantes]
typedef struct {
    OctreeOctant *octants[8];    // 8 subárboles independientes
    FrontierGPU *frontier[8];    // 8 fronteras multipolo
} OctreeGPU;
\end{lstlisting}

Esta partición ofrece ventajas significativas:

\begin{itemize}
    \item \textbf{Paralelización natural}: Los 8 octantes se construyen en paralelo durante la etapa de inicialización.
    Cada thread construye un octante sin contención con los otros.

    \item \textbf{Eficiencia de memoria GPU}: Cada octante se transfiere a la GPU como un bloque de memoria contiguo, evitando la busqueda de hijos por rama como en CPU.

    \item \textbf{Escalabilidad multi-GPU}: En sistemas con múltiples aceleradores, cada octante puede asignarse a una GPU diferente, distribuye la carga de trabajo de forma natural.

\end{itemize}

A diferencia de la versión CPU donde cada nodo se almacena de forma distribuida en arrays separados (SoA), en GPU cada nodo individual se organiza como una estructura compacta \texttt{OctreeNode} (\textit{Array of Structures}, AoS) que contiene los mismos datos en una única unidad de memoria.
Esto se debe a que en GPU el costo de divergencia de control al acceder a múltiples arrays dispersos es mayor que el costo de leer una estructura compacta.
Cada thread de CUDA que desciende por el árbol accede a un único nodo a la vez; tener todos los datos del nodo juntos en memoria maximiza la localidad espacial, mejorando la tasa de coalesced memory access.

Debido a la baja eficiencia de funciones recursivas para recorrer el árbol en GPU, la arquitectura CUDA requiere un enfoque iterativo que evite el uso de stack implícito.
El campo añadido a la estructura \texttt{next} implementa un enlace al siguiente nodo relevante en orden de traversal horizontal, convirtiendo la búsqueda recursiva del árbol en una iteración directa sobre una lista encadenada de nodos no-hoja.
\begin{lstlisting}[language=C,label={lst:octree_node_struct},caption=Estructura OctreeNode]
typedef struct {
    float center_x, center_y, center_z;
    float half_size;
    float mass;
    double com_x, com_y, com_z;
    unsigned int children[8];
    long star_index;
    unsigned int next;
} OctreeNode;
\end{lstlisting}

Debido a la subdivisión por octantes, es necesario representar una porción minimal del resto de subárboles, la frontera multipolo cumple este propósito fundamental.
La frontera multipolo \texttt{FrontierGPU} es la estructura de datos central que representa la aproximación del campo gravitatorio generado por el resto del árbol.
En lugar de enumerar explícitamente todos los nodos que contribuyen a la aceleración de una partícula (lo cual generaría divergencia masiva entre threads), se mantiene una lista compacta de nodos que conforman la frontera válida según el criterio de apertura de Barnes-Hut.

\section{Diseño algorítmico y paralelización}\label{sec:diseno-algoritmico-y-paralelizacion}

En esta sección se describen los algoritmos principales empleados en la simulación y las estrategias de paralelización aplicadas en las versiones CPU (OpenMP) y GPU (CUDA). Se detalla la estructura de datos utilizada para representar las estrellas, la construcción del árbol jerárquico (Octree/OctreeGPU) asociado al método de Barnes–Hut, y las decisiones de diseño que permiten un uso eficiente de memoria y cómputo.

\subsection{Entrada y salida}\label{subsec:lectura-de-archivos}

Dado el volumen de datos manejado (millones de estrellas), las operaciones de entrada y salida (\textit{I/O}) constituyen una parte crítica del rendimiento global del sistema.
Tanto la lectura inicial como la escritura de resultados se han diseñado para ser escalables y eficientes en entornos de cómputo paralelo.

\subsubsection{Lectura}

La lectura se realiza mediante un modelo distribuido por archivos y procesado por bloques, optimizado para entornos multi-hilo:

\begin{enumerate}
    \item \textbf{Distribución de ficheros entre hilos:}
    Se escanea el directorio de entrada y se genera una lista de ficheros CSV válidos.
    Su procesamiento se paraleliza mediante \texttt{\#pragma omp parallel for} con \textit{schedule(dynamic)}, permitiendo adaptarse a diferencias en tamaño de archivo y equilibrando la carga de trabajo entre hilos.

    \item \textbf{Procesamiento por bloques de lectura:}
    Cada fichero se lee mediante \texttt{fread} en bloques de tamaño fijo (\texttt{BLOCK\_SIZE}), evitando cargar el archivo completo en memoria.
    Para manejar líneas cortadas entre dos bloques se mantiene un fragmento residual (\textit{leftover}) que se concatena con la lectura siguiente hasta completar la línea.
    Esta estrategia reduce el número de operaciones de E/S y mejora el rendimiento respecto a \texttt{fgets}.

    \item \textbf{Tokenización y validación:}
    Cada línea se tokeniza utilizando \texttt{strtok\_r}\footnote{La función \texttt{strtok} no es segura en entornos multihilo, por lo que se utiliza su variante \texttt{strtok\_r}.}.
    Se exige exactamente 12 columnas, descartando líneas incompletas o corruptas.
    Asimismo, se filtran valores literales \textit{null} y se aplican restricciones físicas (por ejemplo, color \(0.3 \leq B\!-\!V \leq 2.0\)).
    La conversión numérica se realiza con \texttt{strtod}/\texttt{strtof}/\texttt{strtoul}.

    \item \textbf{Gestión dinámica de memoria:}
    Cada hilo almacena temporalmente sus resultados en una estructura local \texttt{Star}.
    Debido a que no se conoce el número de estrellas que se van a leer, esta estructura se le asigna una capacidad inicial \texttt{capacity}.
    Cuando el número de entradas supera la capacidad asignada, se amplía dinámicamente mediante \texttt{resize\_stars}.
    Finalizado el procesado de cada archivo, los datos locales se incorporan a la estructura global mediante una región crítica mínima (incrementar la capacidad del array global), manteniendo el resto de operaciones (copia de datos) fuera de ella para reducir contención.

    \item \textbf{Compactación final:}
    Una vez procesados todos los archivos, se ajusta la capacidad de la estructura global al número final de estrellas, liberando memoria no utilizada.
\end{enumerate}

\subsubsection{Escritura}

La salida de la simulación se realiza en paralelo, dividiendo el conjunto de estrellas en \textit{chunks} independientes:

\begin{enumerate}
    \item \textbf{Creación del directorio de salida:}
    Se comprueba la existencia del directorio de destino y, en caso necesario, se crea con permisos estándar.

    \item \textbf{Particionado del conjunto global:}
    El vector de estrellas se divide en \(N\) partes aproximadamente iguales, donde \(N = \texttt{num\_chunks}\).
    Si el total no es divisible, los primeros bloques reciben un elemento adicional, garantizando un reparto equilibrado.

    \item \textbf{Paralelización por archivos:}
    Cada bloque se escribe en un fichero independiente mediante un bucle \texttt{\#pragma omp parallel for}.
    Esta estrategia elimina la necesidad de sincronización entre hilos, puesto que no se comparte descriptor de archivo.

    \item \textbf{Optimización mediante buffers grandes:}
    Cada archivo se escribe mediante \texttt{fwrite} utilizando dos niveles de buffering:
    \begin{itemize}
        \item Buffer de flujo de 8 MB para reducir llamadas al sistema.
        \item Buffer interno de gran capacidad (100--500 MB) donde se formatean las líneas antes de volcarlas al fichero.
    \end{itemize}
    Esto minimiza escrituras fragmentadas y maximiza el ancho de banda de E/S frente a usar funciones como \texttt{fprintf}, algo crítico con millones de registros.

    \item \textbf{Registro temporal de simulación:}
    La función \texttt{write\_results} organiza automáticamente los ficheros en subdirectorios por paso temporal (\texttt{step}), facilitando el análisis posterior de la evolución dinámica.
\end{enumerate}

\subsection{Construcción del árbol Barnes-Hut}\label{subsec:version-cpu}
La construcción del árbol octal (Octree) es un paso fundamental en el método de Barnes–Hut, ya que permite organizar las estrellas espacialmente de forma jerárquica para aproximar interacciones gravitatorias lejanas.
Cada nodo del árbol representa un cubo en el espacio, caracterizado por una masa total contenida, el centro de la masa acumulada y el tamaño del nodo.
El nodo puede contener una o varias estrellas (nodo hoja), o 8 nodos hijos (subdivisión del espacio), cada uno correspondiente a uno de los octantes.

El primer paso de la construcción es elegir dónde colocar el nodo raíz y que espacio ha de abarcar.
Este paso es crucial puesto el posicionamiento del nodo raíz condiciona directamente:
\begin{itemize}
    \item Tamaño global del árbol: Puede requerirse la creación de más nodos internos para llegar a las mismas hojas.
    \item Balanceo de las ramas: Si muchas estrellas caen en el mismo octante frente a una distribución equitativa, puede quedar realmente desbalanceado el árbol.
    \item Precisión de los cálculos: Al limitar el tamaño mínimo de un nodo, puede que un nodo hoja contenga más estrellas de las que debería.
\end{itemize}
La función \texttt{compute\_root\_bounds} realiza el cálculo del nodo raíz así como el tamaño mínimo de nodo en 4 fases:
\begin{enumerate}
    \item \textbf{Cálculo del centro de masa global:}
    El objetivo inicial es determinar un punto representativo alrededor del cual construir el nodo raíz.
    Para ello se recorre el conjunto de estrellas acumulando su masa y su contribución ponderada a las coordenadas del centro de la siguiente forma.
    \begin{itemize}
        \item Se inicializan tres acumuladores (\texttt{center\_x}, \texttt{center\_y}, \texttt{center\_z}) y una suma total de masa (\texttt{total\_mass}).
        \item Para cada estrella:
        \begin{enumerate}
            \item Se añade su masa a \texttt{total\_mass}.
            \item Se acumula su posición multiplicada por la masa en cada coordenada.
        \end{enumerate}
        \item Al finalizar el recorrido, cada coordenada acumulada se divide entre \texttt{total\_mass}, obteniendo el centro de masa.
    \end{itemize}

    Este proceso se paraleliza con \texttt{OpenMP} mediante una reducción, ya que cada actualización de los acumuladores es independiente entre sí.
    \begin{lstlisting}[language=C, basicstyle=\ttfamily\small,label={lst:lstlisting5}]
#pragma omp parallel for reduction(+:total_mass,center_x,center_y,center_z)
    \end{lstlisting}
    \item \textbf{Obtención del radio inicial contenedor:}
    Una vez calculado el centro de masa, es necesario estimar el tamaño mínimo del cubo que contendrá a todas las estrellas.
    Para ello:
    \begin{itemize}
        \item Se recorre de nuevo el conjunto de estrellas y se mide la distancia de cada una al centro de masa.
        \item Se conserva únicamente la distancia máxima encontrada, lo que equivale al radio de la esfera más pequeña que cubre el sistema.
    \end{itemize}

    La búsqueda de la distancia máxima también se paraleliza mediante \texttt{OpenMP} con reducción \texttt{max}, aprovechando que cada comparación es independiente de las demás.
    \item \textbf{Refinamiento mediante expansión tipo Ritter:}
    Para evitar que la esfera inicial quede sobredimensionada por la presencia de estrellas aisladas, se aplica una actualización correctiva:
    si se detecta una estrella fuera de la esfera, el centro y el radio se ajustan para mantener la contención minimizando el volumen.
    Este proceso mejora la compacidad del nodo raíz y reduce el número de subdivisiones posteriores.
    \item \textbf{Conversión a cubo y fijación de la escala mínima de subdivisión:}
    Finalmente, el radio obtenido se transforma en el \emph{half-size} del cubo raíz:
    \[
        h_s = 1.1 \, R,
    \]
    añadiendo un margen del $10\%$ para amortiguar errores de redondeo.

    El parámetro \texttt{min\_node\_size} se determina como:
    \[
        \text{min\_node\_size} = \frac{h_s}{\text{min\_subdivisions}},
    \]
    siendo \texttt{min\_subdivisions} un parámetro seleccionado por el usuario.
\end{enumerate}
El parámetro \texttt{min\_node\_size} limita la profundidad del árbol y define la resolución física mínima del modelo.
Cuando un nodo alcanza este tamaño, se deshabilita la subdivisión y se permite que múltiples estrellas coexistan en el mismo nodo.
Esto:
\begin{itemize}
    \item Previene subdivisiones infinitas en regiones densas.
    \item Reduce el coste computacional.
    \item Evita inestabilidades numéricas debidas a separación extremadamente pequeña.
\end{itemize}

Una vez seleccionado el nodo raíz, se insertan secuencialmente las estrellas.
Para cada estrella se realiza una inserción recursiva:
\begin{enumerate}
    \item Se actualiza la \textbf{masa total} del nodo y su \textbf{centro de masa acumulado}.
    \item Si el nodo aún no contiene subdivisiones y su tamaño es mayor que \texttt{min\_node\_size}, se decide en qué octante cae la estrella usando:
    \[
        \mathrm{octante} =
        (\ x > c_x\ ) \cdot 4 +
        (\ y > c_y\ ) \cdot 2 +
        (\ z > c_z\ ) \cdot 1
    \]
    \item Si el nodo hijo correspondiente no existe, se crea con \texttt{octree\_new\_node}.
    \item Si el hijo ya contenía una estrella, entonces:
    \begin{itemize}
        \item Se marca como nodo interno.
        \item Se reinserta tanto la estrella ya almacenada como la nueva.
    \end{itemize}
\end{enumerate}
\begin{lstlisting}[language=pseudo,caption={Inserción de una estrella en el árbol Barnes–Hut},label={lst:insert_compacto}]
OCTREE_INSERT(tree, stars, n, s, min_node_size):
    # Datos del nodo y la estrella
    (cx, cy, cz, hs) <- centro y half-size del nodo n
    (x, y, z, m)     <- posicion y masa de la estrella s

    # Actualizar masa y centro de masa del nodo
    old <- tree.mass[n]
    new <- old + m
    tree.mass[n]   <- new
    tree.com[n]    <- (tree.com[n]*old + (x,y,z)*m) / new

    # Si el nodo no debe subdividirse más: almacenar estrella
    if (2*hs <= min_node_size):
        if tree.star_index[n] == VACIO:
            tree.star_index[n] <- s
        return

    # Determinar octante destino
    oct <- GET_OCTANT(cx, cy, cz, x, y, z)

    # Si el hijo no existe → crearlo e insertar directamente
    if tree.children[n][oct] == INVALIDO:
        child <- CREAR_NODO(tree, centro_desplazado(cx,cy,cz,hs,oct), hs/2)
        tree.children[n][oct] <- child
        tree.star_index[child] <- s
        tree.mass[child] <- m
        tree.com[child]  <- (x,y,z)
        return

    # Si el hijo contiene una estrella → subdividir
    child <- tree.children[n][oct]
    if tree.star_index[child] != VACIO:
        s2 <- tree.star_index[child]
        tree.star_index[child] <- VACIO
        tree.mass[child] <- 0; tree.com[child] <- (0,0,0)
        OCTREE_INSERT(tree, stars, child, s2, min_node_size)
    # Insertar recursivamente
    OCTREE_INSERT(tree, stars, child, s, min_node_size)
\end{lstlisting}
\subsubsection{Consideraciones en GPU}

La implementación en GPU del método de Barnes–Hut conserva la misma estructura lógica que la versión en CPU: primero se construye el octree y posteriormente se utiliza para aproximar las fuerzas gravitatorias.
Sin embargo, la versión acelerada presenta diferencias relevantes en la organización de datos y en el esquema de paralelización.

La principal divergencia radica en el proceso de construcción del árbol.
Mientras que en CPU la inserción se realiza de forma secuencial, en GPU se paraleliza \textit{a nivel de octante}: cada uno de los ocho octantes principales del nodo raíz se construye de manera independiente.
Esto es posible porque, antes de la generación del árbol, las estrellas se reorganizan en memoria agrupándolas por octante.
Dado que el tamaño de los catálogos analizados en este trabajo es grande, resulta esencial evitar duplicaciones de memoria.
Por ello, la clasificación se realiza mediante un ordenamiento \textit{in-place}, lo que permite reestructurar el arreglo de estrellas sin necesidad de utilizar buffers adicionales.

El procedimiento es el siguiente:
\begin{enumerate}
    \item Se cuenta cuántas estrellas pertenecen a cada uno de los ocho octantes del nodo raíz.
    \item A partir de esos conteos se calculan desplazamientos (\textit{offsets}) que delimitan las regiones del arreglo destinadas a cada octante.
    \item Se reordenan las estrellas mediante intercambios internos (\texttt{swap}) de forma que los datos de cada octante queden almacenados de forma contigua en el mismo arreglo.
\end{enumerate}

Una vez completada esta reorganización, cada octante puede ser construido por un hilo de OpenMP independiente, ya que cada uno escribe únicamente dentro de su propia subregión de memoria.
Como consecuencia, la construcción del árbol resulta \textbf{paralela y libre de bloqueos}, sin necesidad de sincronización entre octantes.
El octree resultante es equivalente al obtenido en CPU, manteniendo el mismo número de nodos y la misma estructura geométrica.

Además, tras la construcción del árbol, se generan los ropes, cuyo propósito es permitir el recorrido del árbol sin recurrencia.
Cada nodo almacena un puntero al siguiente nodo que debe visitarse cuando se ha terminado de procesar su subárbol.
De este modo, la navegación del árbol se convierte en un recorrido iterativo eficiente, particularmente adecuado para GPU, donde la recursión está limitada o directamente prohibida.

La construcción de los \textit{ropes} se realiza mediante un recorrido estructural sobre el árbol ya construido.
\begin{lstlisting}[language=pseudo,caption={Construcción de \textit{ropes} en el octree},label={lst:ropes_pseudo}]
BUILD_ROPES(node, next):
    si node = NULL: retornar

    # El rope del nodo apunta al siguiente nodo externo
    node.next <- next

    para i = 0 .. 7:        # recorrer hijos en orden espacial
        child <- node.child[i]
        si child es NULL: continuar

        # Determinar cuál será el rope del hijo
        child_next <- primer hermano válido después de i
        si no existe hermano:
            child_next <- next

        # Llamada recursiva
        BUILD_ROPES(child, child_next)
\end{lstlisting}
Además de la construcción paralela de los octantes, es necesario reintroducir la \textbf{inlfuencia gravitacional entre octantes}.
Al haber separado la distribución original de estrellas en ocho regiones independientes, cada octree parcial sólo contiene información local y, por tanto, no puede por sí solo estimar la contribución gravitatoria del resto del sistema. Para resolver esto, se construye una \textbf{frontera gravitacional} (\textit{frontier}), que actúa como un conjunto compacto de masas equivalentes que representan a los demás octantes externos.

El procedimiento funciona de la siguiente manera:
\begin{enumerate}
    \item Para un octante concreto, se recorre el árbol correspondiente a cada uno de los otros siete octantes.
    \item En cada nodo visitado, se aplica el \textbf{criterio de aproximación Barnes--Hut}:
    \[
        \frac{s}{d} < \theta,
    \]
    donde $s$ es el tamaño del nodo y $d$ la distancia al centro del octante destino.
    \begin{itemize}
        \item Si la condición se cumple, el nodo se \textbf{acepta como una única partícula equivalente}, caracterizada por su masa total y centro de masa.
        \item Si la condición no se cumple, se \textbf{desciende recursivamente} a los hijos del nodo para obtener una representación más fina.
    \end{itemize}
    \item Los nodos aceptados se almacenan en una estructura compacta llamada \texttt{FrontierGPU}, que contiene exclusivamente las masas efectivas necesarias para ese octante.
\end{enumerate}

Este proceso genera, para cada octante, una lista comprimida de fuentes gravitacionales externas, de tamaño reducido en comparación con el árbol completo.
Durante la fase de cómputo de aceleraciones en GPU, cada bloque solo necesita acceder a su propio subárbol y frontera asociada.

De esta forma se evita la necesidad de:
\begin{itemize}
    \item Compartir nodos globales entre bloques
    \item Realizar sincronización entre octantes
    \item Introducir bloqueos que degraden el rendimiento.
    \item Almacenar el árbol completo en cada GPU.
\end{itemize}

El resultado es una versión completamente paralelizable del método de Barnes--Hut que mantiene la misma aproximación física estándar, pero adaptada para arquitecturas masivamente paralelas.

\subsection{Simulación en CPU}\label{subsec:simulacion-cpu}
La simulación en CPU se basa en la integración temporal del sistema mediante un esquema \textit{Kick--Drift--Kick} (KDK), donde las aceleraciones se calculan utilizando el método de Barnes--Hut.
La estructura general del algoritmo se organiza en torno a la construcción del árbol octree, el cálculo de aceleraciones y la actualización de posiciones y velocidades.

\subsubsection{Cálculo de aceleraciones Barnes--Hut}
El núcleo del cálculo de fuerzas es la función \texttt{compute\_acceleration\_bh}, que realiza un recorrido del árbol adaptativo para estimar la contribución gravitatoria sobre una estrella dada.
La función recibe un nodo del árbol y decide si:
\begin{enumerate}
    \item Tratarlo como una \emph{masa efectiva única} (si cumple el criterio de apertura Barnes--Hut).
    \item Descender recursivamente a sus hijos para obtener una aproximación más detallada.
\end{enumerate}

El criterio se evalúa comparando la relación entre el tamaño del nodo y la distancia:
\[
    \frac{s}{d} < \theta,
\]
donde $s$ es el lado del nodo y $d$ la distancia entre el centro de masa del nodo y la estrella objetivo.
Si además el nodo contiene sólo una partícula, se toma siempre como masa puntual.

La implementación incluye varias optimizaciones relevantes:
\begin{itemize}
    \item Las operaciones de acumulación se realizan usando \texttt{fma} para evitar pérdidas numéricas.
    \item Se añade un término \texttt{EPSILON} para evitar divisiones por cero.
    \item Se descarta explícitamente el caso donde la estrella es la misma que la contenida en el nodo hoja.
\end{itemize}

El cálculo de aceleraciones es independiente para cada estrella, por lo que se paraleliza en un bucle OpenMP.
Cada hilo realiza recorridos independientes sobre el mismo árbol, que permanece en memoria de sólo lectura durante esta fase; por tanto, la paralelización es completamente \textbf{libre de bloqueos}.

\subsubsection{Bucle principal de integración}
El bucle de integración temporal realiza:
\begin{enumerate}
    \item \textbf{Half-Kick:} Se actualizan las velocidades usando las aceleraciones actuales.
    \item \textbf{Drift:} Se actualizan las posiciones.
    \item \textbf{Reconstrucción del árbol:} Las posiciones han cambiado, por lo que la estructura espacial debe actualizarse.
    El árbol anterior se libera y se vuelve a construir usando la función \texttt{build\_tree}.
    \item \textbf{Re-cálculo de aceleraciones:} Se evalúan nuevamente las fuerzas usando el nuevo árbol.
    \item \textbf{Half-Kick final:} Se completan las velocidades del paso.
\end{enumerate}

La reconstrucción del árbol en cada paso es necesaria porque las estrellas se desplazan significativamente en cada iteración, y el rendimiento y precisión de Barnes--Hut depende de la calidad de la estructura jerárquica en relación con la distribución espacial actual.

\subsubsection{Reutilización de memoria y eficiencia}
Para evitar overhead innecesario:
\begin{itemize}
    \item Los arrays de aceleraciones \texttt{ax,ay,az} se asignan una sola vez y se reutilizan en cada paso.
    \item La construcción del árbol se hace con un mecanismo de \textit{realocación progresiva} igual que al leer las estrellas para ajustarse dinámicamente al número de nodos necesarios.
    \item Todas las fases que pueden paralelizarse (cálculo de aceleraciones y actualizaciones de estado) se ejecutan bajo directivas \texttt{omp parallel for}.
\end{itemize}

\subsection{Simulación en GPU}\label{subsec:simulacion-gpu}

La versión en GPU mantiene el mismo esquema de integración temporal que la versión en CPU, pero reestructura la organización de datos y el recorrido del árbol para explotar el paralelismo masivo de las GPUs y minimizar transferencias de memoria. La simulación se ejecuta distribuyendo los octantes principales del árbol entre múltiples GPUs, de forma que cada dispositivo procesa únicamente las estrellas contenidas en su región espacial correspondiente.

\subsubsection{Reordenamiento por octantes y distribución entre GPUs}
Antes de cada paso se ejecuta la función \texttt{reorder\_stars}, que reordena las estrellas de acuerdo al octante del espacio que ocupan con respecto a la raíz del árbol.
Esto produce:
\begin{itemize}
    \item Particiones contiguas en memoria con estrellas espacialmente cercanas,
    \item Coalescencia en accesos a memoria en GPU,
    \item y la posibilidad de asignar cada octante a una GPU diferente sin necesidad de copias de subconjuntos dispersos.
\end{itemize}

El número de GPUs disponibles define cuántos octantes se procesan de manera simultánea.
Para un total de $8$ octantes, el número de iteraciones de cálculo es:
\[
    \texttt{iterations} = \left\lceil \frac{8}{\texttt{device\_count}} \right\rceil.
\]

\subsubsection{Estructura del árbol en GPU y recorrido sin pila}
El árbol Barnes--Hut no se recorre recursivamente en GPU. La recursión implicaría un uso intensivo de memoria local y divergencia de hilos. En su lugar se usa:
\begin{itemize}
    \item un \textbf{árbol lineal} almacenado en memoria global,
    \item nodos con punteros a hijos directos,
    \item y un puntero \texttt{next} (\emph{rope}) por nodo que permite avanzar al siguiente nodo relevante sin volver a la raíz.
\end{itemize}

Este esquema elimina completamente el uso de una pila de recorrido en GPU y reduce la divergencia entre hilos dentro del \texttt{warp}, permitiendo un traversal \emph{stackless}:
%
\[
    \text{mientras } node \neq \text{INVALID:}
    \begin{array}{ll}
        \bullet & \text{Si cumple el criterio de apertura (Barnes--Hut), usarlo como masa lejana;} \\[4pt]
        \bullet & \text{Si no, descender al primer hijo disponible;} \\[4pt]
        \bullet & \text{Si no existen hijos, continuar mediante } node.\texttt{next}.
    \end{array}
\]

\paragraph{Decisiones clave de implementación.}
\begin{itemize}
    \item Los nodos se almacenan como estructuras contiguas en memoria global, favoreciendo el acceso coalescente al recorrer el árbol.
    \item El uso del campo \texttt{next} evita tanto la recursión como el uso de pilas auxiliares en memoria local o compartida.
    \item Los cálculos usan operaciones \texttt{fma} (fused multiply-add) para combinar precisión numérica y rendimiento.
    \item Se evita cualquier rama condicional dependiente del hilo, reduciendo la divergencia de \texttt{warp} en nodos cercanos a los criterios de apertura.
\end{itemize}

\subsubsection{Frontera lineal (\textit{frontier})}
Para cada octante se precomputa en CPU una \textbf{frontera lineal} que contiene nodos distantes que ya se sabe que cumplen el criterio de apertura.
Esta frontera se transfiere a la GPU junto con el árbol reducido del octante.
De esta forma se evita trabajo redundante y la GPU no decide qué nodos de niveles superiores incluir.

\paragraph{Consideraciones adicionales.}
\begin{itemize}
    \item La frontera se construye tras separar los octantes, para que cada GPU trabaje solo con la información relevante a su volumen espacial.
    \item En GPU, la frontera se almacena como un arreglo lineal, facilitando su recorrido en un único bucle sin ramificaciones.
\end{itemize}

\subsubsection{Kernel de fuerzas}
Cada hilo GPU procesa una estrella.
El kernel:
\begin{enumerate}
    \item Inicializa aceleración local en registros.
    \item Aplica aceleraciones analíticas directamente en GPU (potenciales halo NFW y bulbo Hernquist).
    \item Recorre el árbol local del octante usando el método \emph{stackless + ropes}.
    \item Recorre la frontera lineal prefiltrada.
    \item Actualiza velocidad con el semipaso (\texttt{c\_dt2}).
    \item Opcionalmente aplica \textit{drift} si es la primera mitad del paso.
\end{enumerate}

\paragraph{Aspectos numéricos y de rendimiento.}
\begin{itemize}
    \item Todas las variables de paso (\texttt{c\_dt}, \texttt{c\_dt2}, \texttt{c\_theta2}, número de estrellas y desplazamiento base) se almacenan en \textbf{memoria constante}, compartida por todos los hilos del kernel.
    \item Las posiciones y velocidades se mantienen en memoria global, pero con acceso coalescente.
    \item La aceleración no se guarda; se aplica inmediatamente a las velocidades y posiciones, reduciendo tráfico de memoria.
    \item El uso explícito de \texttt{rsqrt()} acelera el cálculo de distancias con suficiente precisión para la dinámica estelar.
\end{itemize}

\subsubsection{Transferencia de datos y ejecución en múltiples GPUs}
Para cada dispositivo:
\begin{enumerate}
    \item Se copian las posiciones y velocidades de su rango de estrellas.
    \item Se copian el árbol local y su frontera.
    \item Se lanza el kernel \texttt{compute\_forces\_kernel} en un \texttt{cudaStream} independiente.
    \item Se copian de vuelta las posiciones (si hay \textit{drift}) y las velocidades a CPU.
\end{enumerate}

Las transferencias y el kernel se solapan mediante \texttt{cudaMemcpyAsync}, y se asigna un hilo de OpenMP para gestionar cada GPU, evitando bloqueos.
Cada GPU se sincroniza sólo al final de cada fase, no dentro del kernel, reduciendo los tiempos muertos de comunicación.

\paragraph{Detalles adicionales.}
\begin{itemize}
    \item El cálculo se realiza en doble precisión (\texttt{double}) para estabilidad numérica, pero se usan constantes en precisión simple donde no afecta al resultado (por ejemplo, \texttt{theta2}).
    \item Se emplea una política de \textbf{copiar-construir-liberar} para árboles y fronteras en GPU en cada medio paso, garantizando consistencia aunque se reordenen las estrellas entre pasos.
    \item La función \texttt{compute\_halfstep} coordina la ejecución en paralelo, combinando CUDA y OpenMP sin interferencias entre dispositivos.
\end{itemize}
